# Agent Note: Runs of work fold into one row, and the live action into one line

Status: implemented

[English](2026-11-07-web-activity-fold-and-live-line.md) | 中文

## Problem

Web 会话中的每个事件都占一行：每个 Assistant 步骤贡献一个带单行预览的 `Think` 行，每个工具调用贡献自己的摘要行。于是一个三十步的任务会产生四十多行同等分量的行；又因为轮次运行期间 `ChatView` 会跟随尾部，这一列会以模型的速度从读者眼前滚过。唯一回答「此刻在做什么」的元素——流内的 `Deep diving...` 状态——位于同一个滚动区之内，恰好在最需要它的时候离开屏幕。

密度并不是唯一的问题。流里没有任何东西告诉读者：连续六行属于同一段工作；流外也没有任何东西说明智能体此刻在做什么。

## Decision

**同一轮次内连续的 Activity 节点渲染为一行折叠行。** 一段活动是由自身不带正文的 `assistant-step` 节点与 `tool-call` 节点组成、且共属同一轮次的最长连续序列；`ChatView` 在其他任何节点处、以及每个轮次边界处切分该顺序。折叠行用 `ToolCallView.title`——工具为自己卡片发布的那句标题——列出这段活动执行过的调用，随后是重复次数、推理块数量与该段活动的实际耗时。保持折叠时，它还会预览这段活动最后一个推理块的最后一行。

**展开该行渲染的是它本来就有的席位。** `ActivityGroup` 为每个成员挂载同一个 `ChatNodeSeat`，因此 Think 行、Tool 行、它们的卡片、它们的 Inspect 交接以及展开状态，全都是本 bundle 已有的实现；折叠只增加了一个边界和一份摘要，而没有第二套展示。

**任何回答用户的内容都不被折叠。** 绘制正文、图片或未知块的成员保有自己的席位，并把活动切成两段，因此摘要绝不会包含答案。失败的调用在折叠行上保留失败信息的第一行与错误状态。只含一个节点的活动不构成折叠，按原样渲染。

**从详情面板选中的调用会展开包含它的行。** 从详情面板以及从 Tool 行 `Inspect` 操作进入的查看路径，仍能揭示它指向的调用，因为外部选择优先于该行自身的关闭状态。

**实时动作是一行停靠的行。** `LiveActivity` 以 `order: 10` 注册在 `conversation.input.dock` 上：输入卡片上方的一行，位于滚动区之外，用 Host 标题显示正在进行的调用，或在调用之间显示工作提示，并附带运行中轮次的计时。没有轮次运行时它不渲染任何内容，并取代流内状态，因此「此刻在做什么」只有一个归属，且不会滚走。

**折叠是既有节点之上的展示。** 会话事件、wire 字段和模型输入都没有变化：分组读取的是会话视图本来就持有的 Chat Node 种类与位置，调用标题来自 Host 为调用自己的卡片算出的 `ToolCallView`。分组跟随顺序——某个 key 的种类和轮次从不改变——因此流式 delta 不会重跑分组；而成员通过普通席位所用的同一个按键选择器读取，这正是「中途开始说话的步骤能离开折叠、渲染自己的正文」得以成立的原因。

**Think 行在它渲染的地方保留自己的契约。** 被折叠活动中的推理可通过展开该活动到达；而确实渲染的 Think 行仍然拥有它的尾部跟随实时摘要与展开为完整文本的行为（[思考尾部滚动](2026-08-02-web-thinking-tail-scroll.md)）。

## Alternatives considered

**结算时折叠：轮次运行期间显示明细行，结束后变成一行摘要。** 产品负责人在「从第一行起就保持安静」的方案下否决了它：实时行承担了「正在发生什么」，因此消息流不必是实时表面，`turn/end` 时也不需要回流。

**在新增的停靠行旁边保留流内状态。** 否决：两个元素会回答同一个问题，而流内的那个正是会滚走的那个，并且会重复渲染停靠行已经展示的同一状态。

**由 `ui-tool` 拥有一个用于折叠标题的摘要席位。** 在 `ToolCallView.title` 被证明足够之后否决：工具已经发布了它自己卡片头部显示的句子，新造一个组合点只会重新推导 wire 已携带的字符串，并且会让 `ui-conversation` 的行外观无谓地依赖另一个包的注册生命周期。

**只在折叠行内部决定活动成员。** 否决：该行必须知道活动从哪里开始、到哪里结束，而这是整个有序列表的属性，单个成员看不到自己的兄弟节点。

**在 `ChatView` 内部根据节点内容计算分组成员。** 否决：`ChatView` 刻意不在 Assistant delta 上重渲染（只在顺序变化时重渲染），因此依赖成员文本的活动边界会在该成员开口的瞬间失效。边界判断因此被放在对成员自身的订阅之后。

**整轮次折叠，包含正文。** 否决：它会把助手的答案藏进摘要行，而这是会话绝不能做的一件事。

**在同一次改动中发布持久化的密度偏好（紧凑、均衡、详细）。** 在此推迟，随后作为独立决策发布：这次改动需要的是折叠加展开这个查看入口，而偏好在新的默认值被读过一次之后才落地（[对话密度](2026-11-07-web-chat-density-preference.md)）。

## Consequences

一个长轮次读起来只剩下少数几行：助手的正文、每段工作一行的活动行（并点名这段工作），以及仍然可见的失败。要读某个具体调用做了什么，只需点击包含它的那段活动一次，或走已有的 Inspect 路径进入详情面板；而希望看到完整序列的读者仍可通过 Trajectory 页签获得完整账本。

取舍是真实的。折叠的活动显示调用标题而不显示其参数，因此想知道某条命令究竟跑了什么的读者必须展开该行、或打开该调用的详情。实时行会重复当前调用，即使该调用自己的行也同时在屏幕上——这是有意的重复，因为行会滚动而该行不会。最后一行思考预览只是一个块的一行：它报告智能体在一段活动末尾在想什么，而不是推理的全貌。

验证：`pnpm run test:gui`（3807 通过，1 跳过）覆盖模型、折叠、实时行与 ChatView 集成；`tsc -b tsconfig.client.json` 与 oxlint 均无问题。折叠在手机宽度下的真实几何，以及它在实时模型流中的手感，仍属人工检查，当前环境无法运行。
